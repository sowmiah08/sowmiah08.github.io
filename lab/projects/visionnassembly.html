02 / THE PROBLEM

Assemble parts whose positions you don't know

Nothing about the scene is given to the robot. Each part can be anywhere in the arm's reachable area, at any rotation, partly hidden from the camera, and the sensors are noisy. The system has to see the parts, find each one's exact position and rotation, then pick it up and insert it to millimetre tolerance. When a step fails, it needs to notice and recover instead of carrying on blindly.

Inputs

  • One overhead RGB-D camera
  • Each part's 3D model, built from its simulation model
  • A short YAML file per part: how to grip it and how it mates

Outputs

  • A 6-DoF pose for every part (≈1 mm)
  • A planned grasp → lift → align → insert
  • A verified assembly, or a clear "not found"
03 / HOW IT WORKS

See → locate → act → recover

See

Depth separates the objects from the table, and SAM 2 draws an exact mask around each one.

/camera depth + RGB → per-object masks

Locate

Each part's 3D model (built from its simulation model) is fitted to the masked depth points. That gives its position and rotation.

masked points + model → 6-DoF pose (ObjectPose.msg)

Act

MoveIt plans a straight-down grasp, a lift and a careful insertion.

pose → grasp → lift → align → insert

Recover

If a part isn't found, a grasp misses or an insertion is blocked, the robot re-scans, tries another grasp, or searches around the hole in a spiral.

failure → re-scan | next grasp | spiral search

Evaluate

A test harness randomises the scene and scores every run against the simulator's true poses.

seeded scene → run → summary.json
04 / KEY DECISIONS

What makes it robust

01Parts are data, not code

Adding a new part needs no new code: just its model plus a short YAML file describing how to grip it and how it mates. The peg/plate pair was added this way. Part descriptions live in config/objects/, grippers/ and assemblies/.

02Recovery built into the loop

Every stage can fail, and each failure has its own response: re-scan when a part isn't found, try the next grasp when one misses, spiral-search when an insertion is blocked.

03Honest "not found"

When too little of a part is visible, the system reports it as missing instead of guessing. In the one failed trial only 18% of the peg was visible, and it was correctly reported rather than grasped blindly.

04Measured, not demoed

A seeded evaluation harness randomises position, full 360° rotation, occlusion, depth and RGB noise, and 0–3 mm of injected insertion error. Every trial is scored against ground truth.

  --assembly plug_into_socket --arm left

Practical gotchas I hit

  • NumPy is pinned to 1.26, because NumPy 2 breaks ROS's cv_bridge.
  • Perception runs in a venv with system site-packages, so SAM 2 and the ROS Python packages can both be imported.
  • Perception code must run with .venv/bin/python, not ros2 run, which uses the system Python and can't see SAM 2.

07 / LIMITS & NEXT

What it can't do yet

Known limits

  • The arms can only grasp straight down, within a small reachable area.
  • Only the part's position is randomised. Targets stay in place.
  • Parts that are ≲ 20% visible to the overhead camera aren't found.
  • Simulation only.

Next steps

  • Active perception with the wrist cameras, to look again at hidden parts
  • Larger evaluations: more trials, error sweeps and randomised targets

// 30-second pitch

1 · SEE

Depth finds the objects. SAM 2 gives each one an exact mask.

2 · LOCATE

Fit the part's 3D model to the masked points to get a 6-DoF pose.

3 · ACT + RECOVER

MoveIt grasps and inserts. Re-scan, next grasp or spiral search on failure.

Why use SAM 2 if depth already separates the objects?

Depth tells me where something sticks up from the table. SAM 2 gives the exact outline of each object, so the points I fit the model to belong to that part only. A clean mask means a clean pose.

What happened in the one failure?

Only 18% of the peg was visible to the camera. The system reported it as "not found" instead of grasping blindly, which is the behaviour I want. The fix on the roadmap is to use the wrist cameras to take a second look.

How hard is it to add a new part?

There's no new code. You add the part's model and a short YAML file describing how to grip it and how it mates with its target. I added the whole peg/plate pair that way.

How do you know it actually works?

A test harness randomises the part's position and full rotation, occlusion, sensor noise and injected insertion error, then scores every run against the simulator's true poses. Results go to a summary.json with one log per trial.

What would you do next?

Active perception with the wrist cameras for hidden parts, then larger evaluations with more trials, error sweeps and randomised targets, before moving to real hardware.
