Completed · working on real hardware

02 / HOW IT WORKS

Fingertip pixel → robot joint angles

Find the fingertip

MediaPipe detects the index fingertip in the RGB frame and publishes its pixel coordinates.

/camera/side_camera/color/image_raw → /hand_pixel

Lift it into 3D

The pixel is back-projected into 3D using the aligned depth image and the camera intrinsics.

/hand_pixel + depth + CameraInfo → /hand_3d (camera frame)

Know where the robot is

An AprilTag fixed to the robot base gives the camera-to-robot transform, which is broadcast through TF2.

/detections → TF camera → base_link

Move the arm

The 3D point is transformed into the robot frame. An IK solver from LeRobot computes joint angles and sends them to the arm over serial.

/target_point → IK → motor commands

Built as small ROS 2 packages

Safety built in

  • Motor velocity and acceleration are capped on startup.
  • Targets are clamped to a bounded workspace before IK is solved.
  • The robot returns home when no target arrives, and on Ctrl+C.

04 / HOW I EXPLAIN IT

Talking points

"You point at a depth camera and the robot arm follows your fingertip in real time. MediaPipe finds the fingertip in the image and depth turns that pixel into a 3D point. An AprilTag on the robot base tells the camera where the robot is, so I can express the point in the robot's own frame. Then LeRobot's IK turns it into joint angles."

// 30-second pitch

1 · DETECT

MediaPipe → index-fingertip pixel.

2 · LOCALISE

Depth + intrinsics → 3D. AprilTag → camera-to-robot TF.

3 · ACT

IK → joint angles, sent over serial, with safety limits.

Why use an AprilTag?

The camera sees the hand in its own frame, but the robot needs targets in base_link. A tag fixed to the robot base gives that camera-to-robot transform directly from the image, with no manual extrinsic measurement, and TF2 then handles the conversion.

How do you get 3D from a 2D detection?

I read the aligned depth at the fingertip pixel and back-project it with the camera intrinsics from CameraInfo, using the pinhole model. That gives a 3D point in the camera frame.

How do you keep it safe?

Velocity and acceleration are capped at startup, targets are clamped to a bounded workspace before IK, and the arm goes home when it loses the target or on Ctrl+C.

Why is it split into separate nodes?

Each stage (detect, back-project, transform, control) can be tested and swapped on its own over standard topics. For example, MediaPipe could be replaced with a different hand tracker without touching the control code.
