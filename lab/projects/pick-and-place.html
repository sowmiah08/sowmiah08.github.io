Autonomous pick & place on SO-101

Completed · running on real hardware · next: dual-arm hand-off (planned)

A fully autonomous pick-and-place system on a real SO-101 arm. The robot detects coloured cubes in 3D, plans a collision-free grasp trajectory, closes the gripper, lifts the cube and returns home, then repeats with no human input.

02 / HOW IT WORKS

From point cloud to motor command

Detect cubes in 3D

The RealSense point cloud is masked by colour (HSV), clustered with DBSCAN and filtered by cube shape. Red and blue cubes get separate topics.

/camera/camera/depth/color/points → /cube_red_3d, /cube_blue_3d

Move into the robot's frame

TF2 transforms each detection from camera_color_optical_frame into right_base_link.

PointStamped (camera) → /cube_base (robot)

Commit to a stable target

The last 10 detections are buffered, so the arm doesn't chase noise. Once a goal is committed it's locked until the pick cycle finishes.

10-sample buffer → locked goal

Plan & execute the pick

A MoveGroup action client runs the sequence: home → open gripper → move above the cube → close the gripper (3 s) → lift 20 cm → hold 3 s → open → home.

MoveGroup → FollowJointTrajectory → servos
03 / KEY DECISIONS

The engineering that made it reliable

01Async state machine

The pick sequence is a pure ROS 2 async callback chain, with no time.sleep() blocking the executor. Each step triggers the next through action result callbacks and one-shot timers, so the node stays responsive throughout.

02MoveIt goal design

Each goal has a 5 cm position box around the target jaw pose and a top-down orientation constraint [0, -0.707, 0, 0.707]. start_state.is_diff = True makes MoveIt always plan from the real current joint state.

03Servo drift fix

Joint drift after the gripper closed caused CONTROL_FAILED on the lift trajectory. Setting allowed_start_tolerance = 0.0 in moveit_controllers.yaml stopped those trajectory rejections.

04Tuned for success rate

Planning success improved significantly after relaxing the lift orientation tolerance to 0.5 rad and disabling start-state validation. Home is reached reliably with a direct joint trajectory.

1 · PERCEIVE

Point cloud → HSV mask → DBSCAN → cube-shape filter.

2 · TRANSFORM

TF2: camera optical frame → right_base_link.

3 · ACT

Async MoveIt state machine drives the real servos.

Why wait for 10 detections before moving?

A single point-cloud detection is noisy. If the arm followed every update it would chase noise mid-motion. Buffering 10 stable detections, then locking the goal for the whole cycle, makes the motion decisive and repeatable.

Why not just use time.sleep() between steps?

Sleeping blocks the ROS 2 executor, so callbacks such as joint states and action results stop being processed. I chained the steps with action result callbacks and one-shot timers, so the node stays responsive the whole time.

What was the hardest bug on real hardware?

After the gripper closed, the servos drifted slightly, so MoveIt rejected the lift trajectory with CONTROL_FAILED: the start state didn't match. Setting allowed_start_tolerance = 0.0 and planning from the real current state (is_diff = True) fixed it.

How does MoveIt talk to the robot?

MoveIt sends FollowJointTrajectory goals to test_bridge, which drives the Feetech servos over USB serial with the FTServo Python SDK and publishes /joint_states back.
