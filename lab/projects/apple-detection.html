02 / THE DATA PIPELINE

Most of the work is the data

Collect & combine

Three sources were merged for robustness: the MinneApple benchmark, a Kaggle apple dataset, and a custom set annotated in Roboflow.

MinneApple + Kaggle + custom → final_data/

Masks → YOLO boxes

MinneApple ships segmentation masks, not boxes. For each mask I find the outer contours (RETR_EXTERNAL, CHAIN_APPROX_SIMPLE), take each contour's bounding rectangle, and write it as a normalised YOLO label (class 0, centre x/y, width, height).

mask.png → cv2.findContours → boundingRect → label.txt

COCO → YOLO

Ground truth in COCO JSON is converted to YOLO format: top-left boxes become normalised centre boxes, one label file per image.

ground_truth.json → *.txt

Split & verify

Images are split into train and validation sets, and every image is checked for a matching label (and every label for an image) before training.

2,198 train · 318 val images

Two detectors, same task

YOLOv8s

  • Pretrained yolov8s.pt, fine-tuned

YOLO11s

  • Pretrained yolo11s.pt: 238 layers, 9.4 M params, 21.3 GFLOPs
  • 50 epochs, batch 36, 640×640, about 1.4 h on GPU
  • Validated, then exported to ONNX for CPU inference

How did you turn segmentation masks into boxes?

For each mask, OpenCV finds the external contours, so nested holes are ignored. Each contour's bounding rectangle becomes a box, normalised by the image size into YOLO's centre-x, centre-y, width, height format with class 0 for apple.

Why combine datasets?

One dataset has one orchard, one camera and one lighting condition. Mixing MinneApple, Kaggle and my own Roboflow annotations gives more variety, so the model generalises better. I compared a MinneApple-only model against the combined model to check that.

Why is mAP@50–95 so much lower than mAP@50?

mAP@50 counts a detection as correct when its box overlaps the true box by at least 50%. mAP@50–95 averages over much stricter overlaps, up to 95%. Apples are small and clustered, so finding them is easier than getting every box pixel-perfect.

Why export to ONNX?

ONNX decouples the model from the training framework. The same weights can run on CPU, or through optimised runtimes on edge hardware such as a robot's onboard computer, without the full training stack.
